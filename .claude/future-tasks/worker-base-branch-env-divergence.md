# Settings-branch mismatch has no observable signal beyond a per-cycle log warning

## Priority: P3

Surfaced by the protected-base-branch code review (2026-07-24), finding #8, and
extended 2026-07-30 by the canopy-hardening epic review (PR #183) with a second
instance of the same divergence class (`settingsBranch`). **Both of those
divergences are now closed** (2026-09-08, adopter request #39):

- `CanopyCmsService` gained a `settingsBranch` prop (stamped into the worker's
  `CANOPYCMS_SETTINGS_BRANCH`, validated at synth with the same git-ref guard
  `deploymentName` gets), and `baseBranch` got the same synth-time validation.
- `infrastructure/lib/cms-stack.ts`, as generated by `canopycms init-deploy aws`,
  now imports the adopter's own `canopycms.config.ts` at synth time and derives
  both `baseBranch`/`settingsBranch` from `config.defaultBaseBranch`/
  `config.settingsBranch` directly — so an adopter deploying through the
  generated stack cannot drift the worker's env from the shared config the way
  a hand-copied literal (or a prop nobody ever set) could.
- `docs/deploying-to-aws.md` documents both variables, the derivation, and the
  crash-loop consequence of a wrong `baseBranch` (`verifyBaseBranchExists`
  throwing forever under systemd's `Restart=always`).

See `docs/adopter-migration.md`'s `## Unreleased` entry (#39) for the adopter-facing
description, and `packages/canopycms-cdk/src/constructs/cms-service.ts`'s
`assertValidGitRefComponent`/`baseBranch`/`settingsBranch` doc comments for the
mechanism.

## What remains open: observability

When `config.settingsBranch` and the worker's resolved settings-branch name
DO still diverge — a hand-rolled stack that didn't set the new
`settingsBranch` prop, or a non-CDK deployment — the only signal today is a
per-cycle `workerLogWarn` ("settings branch not owned by this deployment"),
which a shell-less operator never sees.

**Fix sketch.** Surface "a local settings branch exists that this worker does
not own" into `worker-status.json` (`WorkerStatusReport`), so the admin System
Health panel can show it alongside the worker's other health signals, the way
`branch-health.ts`'s `rebaseInProgress` flag surfaces a stuck rebase today.
