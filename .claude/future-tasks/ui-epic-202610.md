# Editor UI/UX epic (int-202610-ui)

## Context

JP asked for a full UI/UX review of the CanopyCMS editor: what is good, what needs to be better, and how. The review covers the shell, forms, drawers, dialogs and admin UIs. Once this plan is approved, this session becomes the **manager** that spawns implementation chips.

How the review was done:

- **Hands-on:** ran a real adopter site on canopycms `0.0.68-int.111`, locally, as dev users *User One* (no edit rights) and *Admin One*.
- **JP's screenshots:** compared against JP's screenshots of that adopter's deployed editor.
- **Code inventory:** walked every editor surface in `packages/canopycms/src/editor/`.

Decisions already made with JP:

- **Restructure the shell**, rather than only polishing it in place.
- **Keep the word "branch."** Make the vocabulary consistent rather than renaming it.
- **Field comments become a hover icon plus a count badge**, replacing the "New comment" link on every field.
- **Sketches A, B and C are approved.** They are written out in full below, with what every control does, so JP can comment line by line.

### Findings from the live session worth knowing up front

- **The gap above the preview:**
  - **Cause.** The editor's header and rail are `position: fixed`, but the panes are in normal document flow and padded only by the header's height (`Editor.tsx` around line 1154). Anything the adopter renders above `/edit` therefore pushes the panes down.
  - **Locally.** The adopter's sticky site header did exactly that. The site footer also sat below the editor, which made the whole page scroll. The size of the gap depended on scroll position.
  - **Why live has no gap.** The adopter added a chrome wrapper to drop its header and footer on `/edit`. The local checkout predated that change.
  - **What's left to fix.** It is still a canopycms bug for every other adopter: the editor must take over the whole window itself (WS1).
  - **The adopter already fixed it in its own code** (a chrome wrapper). After WS1 the adopter **doesn't have to change**: hiding its chrome on `/edit` becomes optional. It is still worth keeping, because it also stops the site's analytics and global fetches from running in the editor (`editor-renders-inside-root-layout-docs.md`). The adopter hand-off note (below) says this explicitly.
- **The blue preview "sync" bar never stops** — JP: usually on live, even though the content shows correctly.
  - **The bar doesn't track page loading.** It tracks one event: the preview page's `usePreviewData` hook posting `canopycms:preview:ready` back to the editor (`preview-bridge.tsx:205`; cleared in `PreviewFrame.tsx`). The page itself renders server-side whether or not that message arrives, so "content looks right but the bar spins" means the message was never received.
  - **There's no timeout**, so a missing ready message means the bar runs forever.
  - **Measured locally on int.111, the bar clears.** A reload and an entry switch (one entry to another) each got a ready message and the bar cleared.
  - **On int.91 it never cleared**, because the preview was the public page, which never sends ready.
  - **Live cause: not yet reproduced.** Likely candidates:
    - the live iframe redirecting (trailing slash or auth) so `event.source` or `origin` no longer matches;
    - views that don't use `usePreviewData`;
    - a ready message sent before the editor's listener re-attaches after a remount.
  - **WS2 step 1** is to capture the messages on live with a console listener and find the real cause.
  - **The fix either way:** clear the bar on the iframe's `load`, and show a missing handshake as a quiet "Live updates off" chip with a reason and a retry (WS2).
- **No longer reproduce on int.111:**
  - the preview showing the home page while editing another entry;
  - the gap (on the live adopter).

## Part 1 — What's good (keep it)

- **The core model is right:** live preview next to a schema-driven form, a branch-first workflow, and Save kept separate from Submit.
- **The protected-branch banner** says why the content is read-only and offers a way forward ("Create a branch").
- **Disabled Save has a tooltip that says why**, e.g. "No changes to save" or "This branch is submitted for review — withdraw it to make changes".
- **Destructive branch actions confirm and explain their consequences.** Deleting an entry or collection that other entries reference lists those entries (`ReferencedByList`), which is excellent.
- **Drafts autosave per branch in localStorage.** A conflict produces specific guidance, and an older-version draft gets an explicit modal.
- **Recovery paths are solid:** the crash screen with "Copy error details", field-level crash fallbacks, and the auth gate's retry states.
- **Field help is good:** field descriptions render under labels, the adopter's descriptions are good, and block templates have labels.
- **The preview bridge** (click-to-focus, highlight marks) is a differentiator. The mismatch indicator is useful, but it is pitched at developers; see WS2.
- **Accessibility groundwork exists:** the navigator has aria-labels on its row menus, and the layout and highlight toggles have aria-labels.
- **The tree's row menus are complete** (Move, Add, Rename, Delete), and the navigator has collapse-all and expand-all.
- **Mantine is a good base.** The theme is generated from brand colours, so restyling is cheap.

## Part 2 — What needs to be better, and how

Severity: **S1** means trust or correctness: the user is misled or loses work. **S2** means friction on daily tasks. **S3** means polish and consistency.

### A. Trust and correctness (S1)

| # | Problem (verified) | Fix |
|---|---|---|
| A1 | **Read-only branches still accept typing.** `FormRenderer` and its fields have no `readOnly` path, so typing on a protected or submitted branch creates drafts and live preview changes that can never be saved. `NoEditPermissionNotice.tsx:11` claims the form is read-only. | Thread a `readOnly` prop (from `branchContentLocked` or missing edit permission) through `FormRenderer` → every field (Mantine `readOnly`, MDXEditor `readOnly`, dropzones disabled, list and block add/remove/reorder hidden). The existing protected/locked **banner stays** as the explanation and the "Create a branch" call to action. Inputs are visibly disabled. No extra lock icon in the form, which would say the same thing a third time. **Fail closed at the choke point**, not only per field. See the WS3 detail under the amendments section. |
| A2 | **The editor's layout doesn't own the window.** The fixed chrome plus the panes in normal flow produce the gap, a scrolling page, and the host footer underneath. Site navigation also stays in the tab order. | Introduce a presentational **`EditorShell`** component, a fixed full-window CSS grid (`position: fixed; inset: 0`). It owns only regions: top bar, rail, side panel, main, and overlays. Feature components (header contents, navigator, preview, form, panels) plug into those regions, and state stays in hooks and context. This also starts breaking up the 1,400-line `Editor.tsx`. Optionally mark host siblings `inert` while mounted. Update `editor-renders-inside-root-layout-docs.md`. See "Component organization" under WS1. |
| A3 | **The preview sync bar spins while the content is already showing.** It waits only for the ready handshake (see Context). | Keep the ready message as the event that clears the bar: clearing on `load` would claim "synced" before the draft reaches the preview, because `onLoad` posts before the preview's listener exists and ready triggers the real re-post. Start a timer on iframe `load`; if no ready message arrives within about 5s, replace the bar with a small "Live updates off" chip, hosted inside `PreviewFrame` until WS2b's toolbar exists. Its tooltip explains that typing won't update the preview until it's reloaded, and it offers a Retry. No change to the bridge's message shapes (`canopycms/preview` is a public contract). First diagnose live (WS2a step 1). |
| A4 | **No clear signal of unsaved state.** Drafts persist in localStorage, so a `beforeunload` nag on every reload would be wrong. | The Unsaved indicator says "Unsaved · kept on this device". Guard `beforeunload` only while a save is in flight or when writing the draft to storage has failed. |
| A5 | **Admin panels render for everyone.** Groups and Permissions are mounted with `canEdit={true}`, and Settings shows admin items to non-admins. | Fold in `admin-panel-client-gating.md`: gate the menu items and drawers on role, and pass the real `canEdit`. |
| A6 | **Missing confirmations.** "Request changes" and "Delete group" happen instantly. List, block and image "Remove" are instant with no undo. | Confirm the branch and group actions. For list, block and image removes, show an **Undo toast** instead of a modal. Undo is a functional update on the *current* `drafts[contentId]` at the list path (never a re-applied snapshot, since `update` closures capture stale values), keyed to branch and entry, reusing the list-item identity keys, and dismissed on entry or branch change. Needs a test. |
| A7 | **Field and entry comment carousels show raw user IDs** (`onGetUserMetadata` isn't passed), while the panel shows names. | Pass the user-metadata resolver everywhere. Show bot owners as "CanopyCMS bot", not `canopycms-content-reader`. |

### G. Media, admin and schema UIs (S3)

- **Media library, scaling to hundreds of assets.** It is our own code (a Mantine `SimpleGrid` with `@mantine/dropzone`), not a third-party library. It loads 40 assets per page with "Load more". **The filename filter only searches pages already loaded**, so with hundreds of images a search silently misses most of them. Changes:
  - **Server-side search** on filename and alt text.
  - **Sort**: newest first (default) or name. Folds in `s3-media-listing-order.md`.
  - **Kind filter**: images or PDFs.
  - **Density toggle**: the current large grid, a compact grid, or a list view showing dimensions, size, upload date and uploader.
  - **"Used in N entries"** on each asset, from the existing asset-refs collector, plus an **Unused** filter so cleanup is possible.
  - **Infinite scroll** instead of "Load more".
  - **Folders and tags are deferred** to the backlog: they need a storage-model change, and search plus "used in" covers most of the need.
- **Media, smaller fixes:**
  - Show the filename, not the slug, on asset cards.
  - Use the same word on the trash icon and in its confirm: "Remove from library".
  - Add upload progress to ImageField.
  - Make the "Insert image" title read "Edit image" when editing.
  - Every MdxImageDialog tab commits the same way.
- **Groups:**
  - Pluralise correctly ("1 member").
  - Confirm deletes.
  - Make result rows keyboard-reachable.
  - Show the batch-save footer as a sticky bar with "N unsaved changes".
- **Permissions:**
  - Make the tree keyboard-operable (or use Mantine `Tree`, as the navigator does).
  - Use consistent wording: "Add group" / "Add user" / "Allow public access".
- **"Schema editor": it is really collection management.**
  - **What it does:** it can't define fields; fields stay in code. It lets you create, rename and delete collections (folders), choose which **code-defined** entry types a collection allows (from the schema registry), set a default type, singletons and max items, and reorder.
  - **Where it lives:** behind "Add Collection" and "Edit Collection" in the navigator, and it writes collection metadata on the branch.
  - **Do now:**
    - Show it to admins only (part of A5).
    - Make Cancel really cancel: today entry-type add and edit save immediately, even inside a dialog that offers Cancel. That is a correctness bug.
  - **Defer** the visual redesign (it uses modal-on-modal-on-modal) to a backlog file; it isn't critical for launch.
- **System health:** match the other admin surfaces (a drawer, opened from Settings).

### H. Visual system, copy and accessibility (S3, cross-cutting)

- **Design tokens in `theme.tsx`:**
  - Spacing, font size and radius scales.
  - Use Mantine component `defaultProps` instead of per-call `size="xs"` and inline styles.
  - Remove hard-coded `grape-6`, `#fff` and `#000`.
- **Copy rules:**
  - Sentence case everywhere.
  - Verb-first buttons.
  - No "successfully".
  - `…` only for in-progress states.
  - Human labels instead of paths in all messages.
  - Developer diagnostics (preview-mark mismatches) go behind a "Details" disclosure, or are shown to admins only.
- **Toasts:**
  - Consistent colour semantics (success green, info blue, warning yellow, error red) and durations.
  - Drop toasts that duplicate a visible result, such as "Comment added" or "Created new entry".
  - Move them bottom-right, away from the content rail.
- **Accessibility:**
  - Give the iframe a `title`.
  - Give every ActionIcon an aria-label and a Tooltip.
  - The dev user picker and group rows become buttons.
  - Use visible focus rings.
  - Check contrast on dimmed xs text (several 11–12px grey labels are below 4.5:1).
- **Responsive:** below about 1024px, default to stacked layout and an overlay content panel. Below 768px, collapse the rail into a top "☰" menu, with editing still possible but preview-first.

## Part 3 — Target design (sketches A, B and C, fleshed out for comment)

### Top bar (48px, single row, both layouts)

| Control | What it does |
|---|---|
| **Breadcrumb** `Pages ▸ About us ●` | Each collection crumb opens the content panel scrolled to and expanded on that collection. The last crumb is the current entry. Its ▾ opens the **Entry menu**: Reload from branch, Discard my changes (disabled with a reason if clean), Rename…, Copy link to this entry, Delete…. The ● dot appears when the entry has unsaved changes. |
| **Read-only lock** (only when locked) | A small "Read-only" chip next to the breadcrumb. Its tooltip gives the reason. The full banner below stays. |
| **Branch pill** `main · Protected ▾` | Shows the current branch and status (Editing / In review / Protected), plus "3 unsaved" when relevant. | **Submit for review** (secondary) | Only on an editable, non-protected branch. Confirms, then opens the PR. Unsaved changes are saved first or block submission, with a clear prompt. Becomes **Withdraw from review** when the branch is in review. |
| **Save** (primary, Mod+S) | Saves the current entry. Disabled with a tooltip giving the reason. "Saving…", then a brief "Saved ✓" inline instead of a toast. If other files have unsaved changes, a split-button caret offers **Save all (N)**. |

It stays the primary explanation of read-only state and is not dismissible. The small top-bar "Read-only" chip exists so the state stays visible while you scroll the form.

### Form (sketch C)

- **Label row:** a `FieldLabel` with the label, a required asterisk, and on the right, the field actions plus the comment control. The comment control is a hover/focus icon, or a persistent "💬 2" badge when threads exist. Clicking it opens an anchored thread popover with the thread list, reply, Resolve and Reopen.

### Component organization (applies to WS1 onward)

"The editor" in this plan means CanopyCMS's editor UI, the `CanopyEditor` tree, never the adopter's page. Taking over the window must not turn `Editor.tsx` into an even bigger god component, so:

- **`editor/shell/`** (new) holds purely presentational layout:
  - `EditorShell`: a CSS grid with named regions (`topbar`, `banner`, `rail`, `panel`, `main`, `overlays`);
  - `TopBar`, `ActivityRail`, `SidePanelHost` (docked or overlay, resizable);
  - `PaneLayout`: the preview/form split, side-by-side or stacked, plus maximize.

  These take children and slots only. They know nothing about branches, entries or APIs.
- **Feature components stay where they are and plug into regions:**
  - the header pieces: breadcrumb, `BranchPill`, `SaveButton`;
  - `EntryNavigator` → the panel;
  - `PreviewPane`, which wraps `PreviewFrame` and the toolbar;
  - `FormPane`, which wraps `FormRenderer`;
  - the Branches, Comments and Media panels.
- **State** stays in the existing hooks. New UI state (panel open and width, layout, preview width, maximize) lives in `useEditorLayout`. `Editor.tsx` shrinks to wiring: hooks in, regions out. This advances `editor-state-context-migration.md` without taking all of it on.

### Amendments from the adversarial plan review

**WS3 — read-only, fail-closed.** Per-field `readOnly` is necessary but not sufficient:
1. **Choke point first.** The single draft writer is the form's `onChange → setDrafts` in `Editor.tsx`; make it a no-op whenever `branchContentLocked` (`currentBranch?.writeBlocked ?? true`) or the user can't edit, and render the form inside a disabled `fieldset`/`inert` container.
2. **Per-field props:** Mantine `readOnly`; MDXEditor `readOnly`, plus the source-mode and fallback textareas; ImageField's Dropzone `disabled`, and crop and replace hidden; BlockField's `DndContext`/`useSortable` disabled (the keyboard sensor too); `FieldCrashFallback` gets no `onChange`.
3. **Custom renderers:** `CustomFieldRenderProps` gains `readOnly`. This is a public-API addition, so the README is updated.
4. **Restored drafts on a locked branch.** Drafts come back from localStorage and from other tabs. Show the saved content, with a notice "You have unsaved changes from earlier on this read-only branch" and a Discard action. Keep the draft until it is discarded; never show it as the editable value.
5. **Tests:** one per field type asserting `setDrafts` is never called under read-only, including MDXEditor's mount-time normalisation.

**WS2a — diagnosis.** Step 1 captures the preview iframe's console errors and whether its effect ran, not only the messages. Candidates in likelihood order:
- (a) the preview's JavaScript never runs (a hydration error, CSP, or a throw in the site's root layout); the server-rendered HTML looks right, but ready is never posted. This matches the symptom;
- (b) a cross-origin preview without `editorOrigin`: `usePreviewData` posts ready to its own origin, so the browser drops it;
- (c) an auth challenge on the deployed tier;
- (d) an `event.source` mismatch after an auth redirect.

Trailing slash and basePath affect draft delivery, not ready.

**WS1 — full-window shell mechanics.**
- **Stacking.** Render the shell through a Portal into `document.body`, so it sits above host chrome by DOM order, below Mantine's drawers (200) and notifications (400).
- **`inert`.** Apply `inert` only to the host app's root, never to body children, because Mantine and Clerk portals live there.
- **Scrolling.** Stop the host document scrolling behind the shell with `react-remove-scroll` (already a Mantine dependency), not a global `body { overflow: hidden }`.
- **Homes for existing state.** Name explicit homes for the two lock banners, the `headerRef` ResizeObserver, and `navigatorOpen`'s URL-derived initial state.
- **Split pane.** Replace the unmaintained `react-split-pane@0.1.92` with `react-resizable-panels`.
