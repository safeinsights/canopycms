# `src/` — Top-level modules

The flat `src/*.ts` modules, kept flat deliberately: measured against the alternative,
the `content-*`/`branch-*`/`url-*` name clusters have 3-6x more inbound traffic from
outside than between themselves, so boxing them into directories would add a hop to
~50 call sites while encapsulating nothing.

Split out of the root [AGENTS.md](../../../AGENTS.md) on 2026-08-23, where this had grown to
914 words inside a single bullet. The **code comment at the point of the rule is
authoritative**; this file is the map to where those rules live.

## Overview

url-collision.ts (the WRITE-boundary half of "no two entries may claim the same `urlPath`" — `findUrlPathClaimant` plus the two directory scans it builds on; the BUILD-time half is `static/index.ts`'s `assertNoDuplicateUrlPaths`, and neither replaces the other since git-delivered content never passes the write boundary while the build guard cannot help an editor authoring the collision right now.

**INVARIANT: keyed on the URL, never on the name.** — an entry beside a same-named sibling collection is legitimate (landing page + folder of children) until that collection gains an index entry; a name-based rule would forbid a shape adopters build. Consumed by content-store.ts's `assertUrlPathAvailable` (create + rename ONLY — blocking an ordinary save would trap the author in an entry they can no longer fix) and by schema-store.ts's collection-rename path. Note `createCollection` needs NO check: collections are created empty, so they cannot contest a URL until an index entry lands in them. `findUrlPathClaimant`'s `isIndexSlug(slug)` branch skips its parent lookup when the collection's OWN name is itself an index slug — a collection literally named `index` collapses onto `<parent>/index`, not `<parent>`, so an entry in the parent whose slug is `index` is the parent's own unrelated landing entry, and matching it there was a false-positive `UrlPathConflictError`; `SchemaOps.updateCollectionInner`'s rename-to-`index` branch has the identical skip for the identical reason), services.ts, build-canopy.ts (`createBuildCanopy`, exported from `canopycms/server` — a one-call factory mirroring `createNextCanopyContext(...)`'s own `getCanopyForBuild()` boot sequence, minus the Next.js pieces, for standalone scripts that run outside a Next.js request/build phase; build/admin only, bypasses all ACLs), content-store.ts (mutator lock keys are namespaced content-ID keys from a directory-scan pre-pass; `ContentStoreOptions.contentRootName` — default `'content'` — is the ID-index scan root and MUST be passed `config.contentRoot`; it was hardcoded, so any non-default content root built the index from a nonexistent directory and every ID-based lookup silently missed while path-based reads kept working; `resolveReferences(data, fields, cache?)` is the public entry point the batch listing surfaces use; a resolved reference carries `ResolvedReferenceMeta` (`id`/`slug`/`collection`/`urlPath`) plus the target's data, with `urlPath` computed by `utils/entry-url.ts`'s `computeEntryUrl` — the SAME call `listEntries` now makes for `item.urlPath`, deliberately not `url-path-resolver.ts`'s reverse url->entry direction. The two now AGREE about index entries (the resolver skips its direct-entry candidate for a literal `index` segment), but the direction still matters: this is the surface that DEFINES an entry's URL, so sourcing it from the consumer of that definition would invert the dependency. The target's body is opt-in via `ReferenceFieldConfig.includeBody`, declared per FIELD because embed-vs-link belongs to the content model and one call routinely contains both kinds; the resolve cache is keyed by id+includeBody so two fields sharing a target cannot have traversal order pick one shape for both — `read()` calls the same walker with no cache, so its behavior is unchanged, and `ReferenceResolveCache` is the per-CALL promise memo documented in [docs/concurrency.md](../../../docs/concurrency.md) that must never be hoisted, persisted or reused across requests), content-listing.ts (`listEntries`' `resolveReferences` option — **opt-in, default `false`, unlike `read()`'s `true`**, because `data` is the caller's own generic and `extract` takes an untyped record, so a flipped default would change a reference from a bare id to an object under every existing call site with no compile error; `createReferenceResolver` + `resolveCollectionItemReferences` are the shared resolution path, applied AFTER the ACL filter and BEFORE `extract`/`filter`; its `readEntryData` now COPIES gray-matter's parsed frontmatter object before merging the body in — gray-matter caches its parse result process-globally keyed by file content and hands every caller the SAME object instance, so mutating it in place leaked one entry's body into an unrelated later `matter()` call's "frontmatter," making a reference resolution to that entry carry `body` or not depending on unrelated listing scope), content-tree.ts (same option, same default, resolved at the `listVisibleEntries` choke point so it covers both entry nodes and the `meta.indexEntry` given to a collection's `extract`

`api/entries.ts`'s admin listing deliberately does NOT resolve — see its `listCollectionEntries` doc comment), entry-link-resolver.ts, git-manager.ts, branch-registry.ts, branch-health.ts (admin-facing scan classifying every dir under a branches root as healthy/corrupt-metadata/orphan, incl. provisioning-lock freshness — mirrors branch-registry's own scan/skip rules so classifications never disagree; `healthy` entries also carry an advisory `rebaseInProgress?: boolean` (via `utils/git.ts`'s `isRebaseInProgress`, modelled on `duplicateContentIds` rather than its own `BranchHealthKind`, since the branch metadata is intact and the state is usually transient) surfacing a clone stuck mid-rebase before the worker's next sync cycle would recover it; consumed by api/admin-branch-health.ts's purge/repair recovery endpoints), sync-core.ts (prompt-free content sync core), dev-content-watcher.ts (dev working-tree↔branch-clone divergence detection.

**INVARIANT:** the watcher/dedupe registry lives on `globalThis`, NOT in module scope — Next's dev server compiles the server graph per route bundle and evaluates each copy in its own module scope, so a module-level `Map` is re-created empty per bundle, every copy arms its own watcher, and the startup warning re-prints on what looks like every request; the duplicated `dev-auth: Auto-configured ...` line is the same effect on a different module-level latch. `lastMessage`/`reportedDivergence` must also OUTLIVE `dispose()` for the same reason — an HMR restart tears the watcher down and immediately arms a new one whose startup check re-finds the same divergence, so dropping the state with the watcher re-prints the block. Divergence is a CONDITION, not an event: `reportOnce` suppresses a verbatim repeat and a retraction is emitted when the trees agree again. The terminal is only half of it — a log cannot hold a condition; see `.claude/future-tasks/dev-divergence-in-app-surface.md`), resource-generation.ts (generalized on-disk generation-marker primitive: per-resource marker under `.canopy-meta/`, bump/read/isGenerationCurrent), content-index-generation.ts (thin wrapper over resource-generation.ts for the ContentId index; `invalidateContentIndexesDurable` is the entry point for content-only mutation sites, `invalidateBranchContentCaches` for bulk working-tree mutations that also bump the schema marker), etc.
