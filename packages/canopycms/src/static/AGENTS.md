# `static/` — Static generation

Framework-agnostic static-generation helpers, and the four build-time guards that keep a published site honest.

## Overview

Framework-agnostic static-generation helpers: `collectStaticPaths` (paths only) and `collectRoutableEntries` (same enumeration, `data`/`updatedAt` carried through) share one internal pass, so both inherit the build-time schema-validity guard — sitemap generation is therefore a new place a production build can go red — and both also inherit the non-fatal `findEntriesWithUnknownKeys`/`warnUnknownEntryKeys` report, which runs immediately BEFORE the throwing guard so a build about to go red still lists everything it found; neither is on `canopycms/server`, matching `findInvalidEntries`/`assertBuildEntriesValid`.

### Guard 3 — no two entries may claim the same `urlPath`

A THIRD check, and the only one exported, is `findDuplicateUrlPaths`/`assertNoDuplicateUrlPaths`, enforcing that no two entries claim the same `urlPath`; deliberately formulated on `urlPath` rather than on names, so the legitimate landing-page-entry-beside-a-sibling-collection shape (no index entry, nothing contested) stays allowed while case-only and merge-delivered same-slug collisions are caught.

### Guard 4 — every listed slug must actually be routable (runs FIRST)

A FOURTH, `findUnroutableSlugs`/`assertRoutableSlugs` (also not on `canopycms/server`, matching `findInvalidEntries`/`assertBuildEntriesValid`), closes a gap the other three don't: the filename grammar (`utils/typed-filename.ts`'s `parseTypedFilename`) allows a slug to contain characters — a dot, most commonly — that `parseSlug` rejects, and `readByUrlPath` runs every URL-resolution candidate through `parseSlug` before trying a read. A listed entry whose slug fails that check builds, gets a `generateStaticParams` entry and a sitemap `<loc>`, and then 404s on every visit — breaking the `Round-trip safe` contract `content-listing.ts` documents on `urlPath`. Run FIRST among the four, ahead of schema validity and duplicate URLs, since an unroutable entry has no URL at all as far as the other three are concerned. Its WRITE-boundary half is the `[SLUG]` guard in `content-store.ts`'s `write()` (plus a clearer-messaged fast path in `api/content.ts` and a `parseSlug` check in `renameEntry()`), exactly mirroring the url-collision.ts/`assertNoDuplicateUrlPaths` pairing below — neither replaces the other, since git-delivered and hand-authored content never passes the write boundary.

### INVARIANT — slug enforcement is create/rename only

That enforcement is **create/rename only**, and `parseSlug` must NOT be pushed down into `ContentStore.resolvePath`/`validateSlug`, which are on the READ path — an entry that already carries a non-conforming slug has to stay readable, saveable and renameable, because renaming it is the only way to clear this build failure; tightening the resolver instead converts a red build into unreachable data. All four run on the RAW listing, before the caller's `filter` — `rootPath` scoping narrows them, `filter` deliberately does not. `findDuplicateUrlPaths` is exported from `canopycms/server` so adopters stop hand-rolling the scan; `canopycms-next`'s `dedupeSitemapItems` stays as the non-build-mode and `extraUrls` half.

### INVARIANT — an index entry answers at exactly one URL

This forward rule and `url-path-resolver.ts`'s reverse one must keep agreeing about how many URLs an index entry answers at — exactly one, its collapsed collection path, which is why the resolver skips its direct-entry candidate for an index segment. Both sides route that one decision through `utils/entry-url.ts`'s `isIndexSlug` (case-INSENSITIVE, since the resolver is the only consumer handling a raw un-normalized URL segment); a bare `slug === 'index'` is the bug that shipped and had to be fixed in review, because it left `/x/Index` answering after `/x/index` stopped

## `seo.ts`

pure `extractSeoFields` (empty-string-is-unset, because Canopy stores optional fields present-but-empty) plus `isNoindexEntry`, THE single `noindex` predicate that must feed both advertising surfaces (`robots: {index:false}` and sitemap exclusion) — deriving them separately is what let a noindex entry stay in one surface while absent from the other; enumeration must never filter on it, since noindex means "don't advertise", not "don't build". `resolveSeoUrl` checks absolute-URL-ness BEFORE normalizing (the reverse order rewrites an off-site canonical into `<siteUrl>/https://…/`); that check and the prefix join now live in `utils/url-prefix.ts`'s `joinUrlPrefix`, shared with `assets/asset-url.ts` so the two cannot drift again — but the SCHEME rule is deliberately NOT shared (`isUnprefixablePath`): a mount point passes `data:`/`mailto:` through, a site origin must still root them, and sharing that silently made `resolveSeoUrl('mailto:a@b.c', {siteUrl})` drop the origin. Next adapter: `canopycms-next/src/static.ts`'s `generateContentSitemap`/`entryToMetadata`, both bound onto `NextCanopyContextResult`. `trailingSlash` is an explicit option on both — Canopy has no knowledge of `next.config`. `generateContentSitemap`'s `pathFor` overrides the URL an entry is advertised at while keeping it INSIDE the entry walk, so the `noindex` gate, the `updatedAt` `lastModified` default and `priority` all still apply — the capability `extraUrls` structurally cannot offer, since an extra URL has no entry to derive them from. A `null`/`undefined` return means "keep the structural path", NOT "drop the entry": dropping stays `exclude`'s job, because a `pathFor` whose natural callback (handle one type, null for the rest) silently omitted every other entry would re-introduce the quietly-short sitemap this module exists to prevent. `pathFor` rewrites happen AFTER `assertNoDuplicateUrlPaths` has run on the raw listing, so a collision it creates is caught only by `dedupeSitemapItems`' warning, never by the build guard. It is deliberately NOT used in `apps/example1`, whose `home` is a root `index` entry (`home.index.<id>.json`, `urlPath: '/'`) precisely so the reference app teaches the modelling that needs no option — and note that re-modelling like that breaks a SLUGLESS `read({ entryPath: 'content/<type>' })`, because `content-store.ts`'s `effectiveSlug = slug || schemaItem.name` defaults the slug to the entry-type name — passing `slug: 'index'` explicitly still resolves. This modelling used to expose a hole: `resolveUrlPathCandidates`' index-fallback candidate for `/<typeName>` is `{entryPath: 'content/<typeName>', slug: 'index'}`, and since `content/<typeName>` is a registered entry-TYPE item, `buildPaths` delegates it to the parent collection and resolves that collection's index entry — so a root index entry also answered at `/<typeName>`, breaking the one-URL invariant above. It is closed now, but deliberately not by narrowing either of those: `resolveUrlPathCandidates` stays pure and schema-free, because telling an entry-type candidate from a collection one needs the branch's schema, which this module doesn't have; `buildPaths`' entry-type delegation stays too, because it is what makes `read({ entryPath: 'content/<type>' })` address a singleton structurally, a supported API narrowing it would break. The gate lives one layer up instead, in `content-reader.ts`'s `ReadContentInput.urlAddressableOnly` (set by `readByUrlPath` and nothing else): it requires every candidate's `entryPath` to be an actual collection (`ContentStore.isCollectionPath`) and the resolved entry's on-disk type to be one the collection declares (`ContentStore.declaresEntryType`) — the same gate that also closes `/<collection>/<typeName>/<slug>`, the sibling family this candidate shape opens for every entry in the collection, not only its index entry
