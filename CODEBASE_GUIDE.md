**Repo-level build scripts** (`scripts/`, root, shared by all five packages' builds):

| File                  | Purpose                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| add-js-extensions.mjs | `addJsExtensions(dir)` — rewrites extensionless relative imports in a built ESM `dist/` to explicit `.js` (or `/index.js` for directory specifiers), since `tsc` with `moduleResolution: "Bundler"` preserves bare specifiers that Node's native ESM resolver rejects (`ERR_MODULE_NOT_FOUND`). Each package's build invokes this against its own `dist/` after `tsc`; `packages/canopycms/scripts/postbuild.mjs` imports it rather than duplicating it (it also has CLI-specific postbuild steps: template-file copying, tsx-shebang stripping, esbuild bundling of CLI entrypoints)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| check-esm-imports.mjs | `pnpm check:esm` — regression guard for the above: builds a sandbox with the 5 published packages' real `dist/` + merged `publishConfig`-over-`package.json` (mirroring what `npm publish`/`pnpm pack` produce) and actually imports every non-skipped `exports` subpath under plain Node ESM, failing loudly on any `ERR_MODULE_NOT_FOUND`. Must run after `pnpm build`; `checkCoverage()` fails fast if its hand-maintained per-subpath `test`/`skip`/`devOnly` list drifts from a package's real `exports` map. Each subpath is exactly one of `test` (imported for real), `skip: <reason>` (published but can't be exercised this way), or `devOnly: <reason>` (workspace-internal, present in dev `exports` but deliberately absent from `publishConfig.exports` — e.g. `canopycms/test-utils`); `devOnly` is enforced, not just declarative — `checkCoverage()` asserts such a subpath is genuinely missing from `publishConfig.exports` AND that every other subpath is genuinely present in it, in both directions, which is what would have caught `./test-utils` having been advertised in `publishConfig.exports` for a while without ever being built                                                                                                                                                                                                                                                   |
| bump-version.mjs      | Sets the version across all 5 publishable packages in lockstep (patch-bump, explicit version, or `--min <version>` — patch-bumps from `max(committed, given)`). `--min` exists because the committed version is not a reliable record of what was actually published: `publish.yml` commits the bump only AFTER all five packages publish, so a run interrupted in between leaves npm holding a version main doesn't know about, and re-deriving from the stale committed value fails every subsequent `npm publish` with "cannot publish over previously published version" until a human intervenes. `publish.yml`'s stable path passes the npm registry's current `canopycms` version as `--min`, making an interrupted publish self-healing instead of wedging the release train. The explicit-version form accepts a full semver `-prerelease`/`+build` suffix — validated against semver's identifier grammar (no leading zero on a numeric prerelease identifier, no empty dot-separated segments), not just `x.y.z` — because `publish-prerelease.yml` passes `prerelease-version.mjs`'s `X.Y.Z-int.N` output straight through; `--min` itself stays strict `x.y.z`, since a prerelease has no meaningful ordering against a stable release. The validator returns the canonical TRIMMED string, which is what gets written, closing the gap where the validated string and the written string could differ |

### Auth Plugin Verification Allowlist

Fail-closed guard (SEC-C1) against a dev/insecure auth plugin accidentally serving prod traffic. `AuthPlugin.verifiesCredentials?: boolean` (auth/plugin.ts) is an allowlist, not a denylist: a plugin must affirmatively set it `true` to be usable when `mode: 'prod'`. `assertAuthPluginAllowedForMode(plugin, mode)` throws otherwise, and is called against the plugin BEFORE any wrapping — e.g. by `createNextCanopyContext()` (canopycms-next/context-wrapper.ts) and `http/handler.ts` — so `CachingAuthPlugin` can't hide an unset marker. `ClerkAuthPlugin` (canopycms-auth-clerk) sets `verifiesCredentials = true` (real JWT verification); `DevAuthPlugin` (canopycms-auth-dev) deliberately leaves it unset so it fails closed if ever pointed at `mode: 'prod'`.

### Permission Model

- Groups-only (no roles) - users belong to groups with associated permissions
- Reserved groups: "Admins" (full access), "Reviewers" (can review/approve PRs)
- Path-based ACLs: Define who can edit specific files/trees
- Bootstrap admin: CANOPY_BOOTSTRAP_ADMIN_IDS env var

### Auth Flow

1. Host app provides getUser function to adapter
2. AuthPlugin.verifyUser validates external token
3. User mapped to CanopyUser with groups
4. Permission checks use path ACLs + group membership

**Production (Lambda) auth flow**:

1. CachingAuthPlugin verifies JWT locally (TokenVerifier)
2. User/group metadata looked up from FileBasedAuthCache (EFS JSON files)
3. Cache is populated externally by EC2 worker (refreshClerkCache or refreshDevCache)

## Worker Module

**Location**: packages/canopycms/src/worker/

The CMS Worker daemon handles operations that Lambda (with no internet) cannot perform.

**Module map** (split 2026-08-23): `cms-worker.ts` was 2,949 lines holding four disjoint call trees under one entry point (`start()`). Each cluster is now its own module, reached through a `WorkerContext`. Imports run ONE WAY only — `cms-worker` → {`task-runner`, `git-sync`} → `rebase` → `history-rewrite` → `worker-context`. `pnpm lint:cycles` (dependency-cruiser) enforces only that the graph stays ACYCLIC — a new `rebase.ts` → `task-runner.ts` edge would pass lint and still break the layering, so keep the direction by review. Full invariants live in [worker/AGENTS.md](packages/canopycms/src/worker/AGENTS.md); the file table below adds the daemon's supporting files (`log.ts`, `task-queue*.ts`, `worker-status.ts`).

**CmsWorker responsibilities** (the class keeps a thin delegating method for each; the implementations live in the cluster modules above):

- Process queued tasks from Lambda (push branches, create/update PRs, convert to draft, close PRs, delete remote branches)
- `ensureRemoteGit` (stays in cms-worker.ts — it is provisioning, not a cluster) provisions/self-heals the shared bare repo (`remote.git`); its `scrubPersistedRemote` guarantees the config carries no `remote.origin.url` after a token-bearing clone — a persisted token on shared EFS would let a compromised Lambda read and exfiltrate it. Fails CLOSED: an unreadable config read is treated as "token might still be there," never as "absent," and it re-reads after `removeRemote('origin')` and THROWS if the URL still resolves, rather than swallowing a failed scrub. Now also re-runs on the already-exists fast path (previously fast-returned without re-checking), so a token that survived one interrupted scrub — e.g. a clone crash between `git clone` and the scrub — no longer survives forever
- Sync bare repo (remote.git) with GitHub on a schedule; each cycle also pushes THIS deployment's own settings branch (`pushSettingsBranches()`, private, git-sync.ts) — narrowed to `this.settingsBranch` only (previously pushed every local `canopycms-settings-*` branch); any OTHER such branch found locally (reconciled in via the tracking-namespace fetch, signalling another deployment shares this repo) is warned about but never pushed; the swallowed-error warning is more specific when the swallowed error is itself a non-fast-forward rejection (`isNonFastForwardRejection`, utils/git.ts)
- `pushBranchToGitHub` (private, task-runner.ts) classifies push failures via `isNonFastForwardRejection` (utils/git.ts) and throws `PermanentTaskError` (fail-fast, skips the task's retry budget) on a non-fast-forward rejection — the branch moved on GitHub (another deployment sharing the repo, or a direct push) and retrying the identical push can never succeed; requires stable English git output, so the push's simple-git instance is configured with `gitChildEnv({})` (git-manager.ts, forces `LC_ALL=C`/`LANG=C`)
- `updateBranchMetadataOnFailure` (task-runner.ts) records the (already-redacted) failure reason into `BranchMetadata.syncFailureReason` alongside `syncStatus: 'sync-failed'`, so the editor can show WHY a sync failed, not just that it failed; `updateBranchMetadata` (success path) explicitly clears `syncFailureReason` on the next successful sync (a stale reason would otherwise survive forever, since `save()`'s merge only overwrites keys present in the update)
- Fast-forward the base branch's own workspace clone (`content-branches/<base>`) to `origin/<base>` each sync cycle (`refreshBaseBranchWorkspace()`, private, git-sync.ts) — ff-only (a non-fast-forward is treated as should-never-happen and left untouched); bumps content-index caches on fast-forward; clears stale conflictStatus/conflictFiles left over from before the base branch was excluded from the rebase loop
- Poll GitHub for `submitted`/`approved` branches' PR resolution (`pollMergeState()`, private, rebase.ts — it lives there because the rebase loop is its only caller) — merged branches auto-archive via `buildMergedBranchUpdate` (shared with the manual `markAsMerged` API); closed-without-merge branches get `pullRequestState: 'closed'` recorded only (no status change — an admin decides next steps); best-effort, failures logged and retried next cycle
- Rebase active branch workspaces when upstream changes (resolve-and-continue strategy with ContentId-based conflict tracking)
- Sweep expired `.trash-*` branch directories once per `syncGit()` cycle (`cleanupTrashedBranchDirs()`, private, git-sync.ts, called alongside the existing `cleanupOldTasks()`) — removes dirs the admin purge endpoint (`api/admin-branch-health.ts`) renamed to trash more than 30 days ago; age comes only from the directory name's embedded timestamp, never mtime (rename preserves the source's original mtime); names that don't match the expected `.trash-{dirName}-{STAMP}` shape are left alone and logged
- Refresh auth metadata cache (pluggable callback)

**Rebase conflict handling** (`rebase.ts`'s `runRebaseCycle`/`rebaseOneBranch`, reached through the class's delegating `rebaseActiveBranches()`):

1. Before the dirty check, recovers an INTERRUPTED rebase left by this worker's own prior crash/OOM/spot-interruption (`isRebaseInProgress`, utils/git.ts) — otherwise a wedged clone would read `skippedDirty` forever while `branch-health` scanned it as healthy. `git rebase --abort` is NOT lossless (hard-resets tracked files to pre-rebase HEAD), so every working-tree file the abort will discard is logged by path first, keyed on the git-status WORKING-TREE column only: `M ` (index=M, wd=' ') is the interrupted replay's own cleanly-merged, already-staged file — committed history, not collateral; ` M` (wd=M) is an editor's save landing while the worker was down — genuinely discarded, and logged; `??` is left alone by the abort. KNOWN GAP: a save onto one of the rebase's own conflicted (`UU`) paths cannot be distinguished from the conflict itself, so that discard goes unlogged
2. Skips the base branch's own workspace dir (refreshed separately by `refreshBaseBranchWorkspace()`, not rebased) and branches with uncommitted changes (dirty tree); previously-silent skips are now logged
3. For branches that are `submitted`/`approved` (in review, not rebased under an active PR): still polls GitHub for PR resolution via `pollMergeState()` before skipping, since nothing else signals a merge/close back to the worker
4. On conflict: applies `--theirs`/`add` (the branch's version in rebase context) to keep editor work for ordinary conflicts; MODIFY/DELETE conflicts have no "their version" to check out (`git checkout --theirs` exits non-zero on one) and are resolved from the index/working-tree status pair instead — `UD` ("deleted by them": the branch deleted it) → `git rm`; `DU` ("deleted by us": the branch modified it) → `git add`. A per-file resolution failure is caught and routed into the `!completed` abort-and-record path rather than rethrown — an escaping throw here used to skip both `rebase --abort` sites and wedge the clone mid-rebase forever, since this resolution code IS the round loop's own catch
5. Records conflicting files as `ContentId[]` in `BranchMetadata.conflictFiles`
6. For `.collection.json` files: extracts ContentId from the parent directory name; falls back to `ROOT_COLLECTION_ID` for the root content directory
7. Non-entry files with no extractable ContentId are excluded from `conflictFiles`
8. Test files: `worker/cms-worker-rebase.test.ts` (11 integration tests using real git); `worker/cms-worker-rebase-wedge.test.ts` (the two ways a clone was left wedged mid-rebase forever — a modify/delete conflict escaping the round loop's catch, and worker termination mid-rebase — plus the collateral-file logging: a bystander file predating the rebase stands in for an editor's concurrent save, a file replayed-and-staged by the rebase itself must NOT be reported as discarded)

**Directory structure** on filesystem:

```
.tasks/
  pending/      -- ready to be picked up
  processing/   -- currently being executed
  completed/    -- finished successfully
  failed/       -- permanently failed (exhausted retries)
  corrupt/      -- unreadable files moved here for inspection
```

**Key features**:

- FIFO ordering by createdAt with stable tiebreaker
- Retry with exponential backoff (5s -> 10s -> 20s -> 40s -> 60s cap)
- Crash recovery: recoverOrphanedTasks moves stale processing/ tasks back to pending/
- Deduplication: skips tasks that already exist in completed/ or failed/
- Auto-cleanup: completed/failed tasks deleted after 30 days

### Dual-Build Support (`withCanopy` staticBuild option)

`withCanopy()` supports a dual-build convention where CMS-only files use `.server.ts` / `.server.tsx` extensions (e.g., `route.server.ts`, `page.server.tsx`), and static-export-only page variants use `.static.ts` / `.static.tsx` (e.g., `page.static.tsx`).

| `staticBuild` value | Behavior                                                                                                                                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `false` (default)   | Adds `server.ts` and `server.tsx` (`CMS_PAGE_EXTENSIONS`) to Next.js `pageExtensions`, so `.server.ts`/`.server.tsx` files are processed (API routes, editor page, and a route's server-build page variant) |
| `true`              | Adds `static.ts` and `static.tsx` (`STATIC_PAGE_EXTENSIONS`) instead, so Next.js processes a route's static-export-only page variant (e.g. `page.static.tsx`) and ignores `.server.*` CMS-only files        |

**Convention**: CMS-only routes (catch-all API handler, editor page) use `.server.ts`/`.server.tsx` extensions. This lets a single repo produce two build outputs: a full CMS build (dev/server) and a static export with zero editor code.

**Split-page content routes**: a content route can also ship two page variants for the same URL — `page.static.tsx` prerenders at build time (`export const dynamicParams = false`, required by `output: 'export'`) and `page.server.tsx` renders per-request (`export const dynamic = 'force-dynamic'`, no `generateStaticParams`) so path ACLs apply and unknown slugs 404 instead of throwing Next's internal `NoFallbackError`. Because Next.js statically parses route-segment config, a single shared page file cannot switch these behaviors on an env var — hence the two file variants, selected by which one `pageExtensions` includes for a given build.

```typescript
const isCmsBuild = process.env.CANOPY_BUILD === 'cms'
export default withCanopy(
  { output: isCmsBuild ? 'standalone' : 'export' },
  { staticBuild: !isCmsBuild },
)
```

**CI verification**: apps/dual-build-fixture/ is a minimal Next.js app that exercises this convention for real — `dual-build.test.ts` (vitest) shells out to `next build` twice (`CANOPY_BUILD=static` and `=cms`) plus a `next start` smoke check, asserting the static export has zero Mantine/editor code and no `/edit` or catch-all API route, the cms build has both, and both builds read the same content entry. Not an adopter-facing example — see [Test Organization](#test-organization) below. CI job `dual-build` in `.github/workflows/ci.yml` runs it, gated by a `dorny/paths-filter` step (not a workflow-level `paths:` trigger, so the job always reports a status) on changes under `packages/canopycms-next/**`, `packages/canopycms/src/cli/template-files/**`, `packages/canopycms/src/build/**`, `packages/canopycms/src/static/**`, or `apps/dual-build-fixture/**`. `apps/dual-build-fixture/canopycms.config.ts` deliberately pairs `defaultBranchAccess: 'deny'` with `defaultPathAccess: { read: 'allow' }`, making its anonymous `/` read (asserted 200 in the cms build) the end-to-end regression test for `checkBranchAccessWithDefault`'s protected-base-branch grant (authorization/branch.ts) — without that grant an anonymous request can't reach the base branch at all under `'deny'`.

### Asset URL prefixing (stored vs rendered)

| Concern  | Function                        | Value                                                                                                                                                                                                                                                                      |
| -------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stored   | `assetSrc(meta)` (asset-src.ts) | Always root-relative (`/assets/…`). Never carries an origin or a deployment prefix — content moves between branches and environments. Structural: both write paths (`ImageField.tsx`'s `commitAsset`, `MdxImageDialog.tsx`'s `handleSave`) store the raw `AssetRecord.src` |
| Rendered | `assetUrl(ref, { baseUrl })`    | The ONLY place a prefix is applied, via `joinUrlPrefix` (utils/url-prefix.ts). Never written back                                                                                                                                                                          |

`baseUrl` is a per-render option rather than a config field because the editor and the public site can legitimately have different answers. Two legitimate shapes, alternatives and never composed: an absolute origin (`media.publicBaseUrl`, validated as an absolute URL, threaded to the editor as `CanopyClientConfig.assetBaseUrl` → `Editor`'s `assetBaseUrl` prop → `AssetContext`), or a same-origin path prefix.

**Routes and assets are two different URL spaces.** `CanopyConfig.basePath` (the deployment prefix — see [Configuration Module](#configuration-module)) is deliberately NOT the asset mount point; which one applies is topology-dependent:

| Asset topology                                                    | Who serves `/assets`                                   | Correct `baseUrl`                                                                                             |
| ----------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| local/lfs adapter, `next dev`, or S3 with no distribution         | Next, via `withCanopy`'s `/assets/:path*` rewrite      | The deployment `basePath` (Next auto-prefixes its own rewrites)                                               |
| CloudFront/CDK (`canopycms-cdk` `AssetSupport`, asset-support.ts) | CloudFront behaviors anchored at the distribution ROOT | None — a Next `basePath` does not move them, and the transform Lambda rejects anything not under `/assets/t/` |
| Assets on a separate origin                                       | That origin                                            | `media.publicBaseUrl` (absolute)                                                                              |

There is also deliberately no `basePath` parameter on `assetUrl`: that name already means something else on `collectStaticParams` (canopycms-next/src/static.ts) — the route prefix of a nested catch-all, where it _filters_ enumerated entries. Passing a deployment prefix there silently yields zero static params and a green build with no pages.

### Transform URL shape

`/assets/t/{directives}/{hash32}/{slug}.{ext}` — `{directives}` is either the literal `orig` (identity: EXIF-strip only, no resize/format/quality change) or comma-separated `key=value` pairs: `w=` (width, multiple of 160 in [160,4096]), `f=` (`webp`/`jpeg`/`png`, must match `{ext}` when present), `q=` (quality 1-100), `c=` (normalized crop rect `x:y:w:h`, four floats in [0,1]). Dev-mode lazy transform emulation — cache-miss under `assets/t/` → parse directives → load original via the asset store → `applyTransform` → write back under the canonical key → serve — lives in `api/assets.ts`'s internal `serveLazyTransform` helper. The prod transform Lambda (`packages/canopycms-cdk/lambda/asset-transform/handler.ts`, mounted by `AssetSupport`) runs the same `applyTransform` engine; both forward that function's real rejection status (400/413/422) rather than flattening it.

### Isomorphic exports (package main entry)

`assetUrl`, `assetSrcSet`, and types `AssetRef`/`AssetUrlOptions`/`OutputFormat`/`CropRect`/`TransformDirectives` are re-exported from the package's main `index.ts` (client-safe, no `node:` imports) alongside the existing isomorphic exports (`sanitizeHref`, config types, etc.).

### Dependencies

`sharp` (^0.35.3) — runtime dependency of transform.ts only (packages/canopycms/package.json); not used by any isomorphic module in this directory.

### Content Model

- **Collections**: Containers for entries (posts, authors)
- **Entry Types**: Define content structure within collections; `maxItems: 1` for single-instance entries
- **Fields**: text, select, reference, object, code, block, markdown, group. Reference fields scoped by optional `collections` and/or `entryTypes` (at least one required; validated by `ensureReferenceFieldsHaveScope`). `group` fields (InlineGroupFieldConfig) are visual-only — they group child fields in the editor UI without adding a data key; all child values are stored flat in the parent object.
- **Field flags**: `isTitle` (marks one string-type field per schema as the display title; validated at registry load time; used by `resolveEntryTitle` fallback chain in `utils/title-field.ts`), `isBody` (marks one markdown/mdx field per schema as the file's body content; at most one per schema; validated at registry load time via `utils/body-field.ts`)
- **Format**: MD/MDX/JSON/YAML with frontmatter (gray-matter for md/mdx); JSON and YAML are data-only formats (no body/frontmatter separation)

### ContentTreeExtractMeta<TEntryTypes>

The second argument passed to `extract(data, meta)`. `buildContentTree<T, TEntryTypes>` accepts an optional second type parameter; `TEntryTypes` defaults to a loose `Record<string, unknown>` shape so existing callers are unaffected. ### Schema Definition

```typescript
import { defineCanopyConfig } from 'canopycms'

defineCanopyConfig({
  contentRoot: 'content',
  mode: 'dev', // required — no default (SEC-C1)
  deployedAs: 'static', // or 'server' (default)
  // ...
})
```

**`mode` is required**: unlike `deployedAs`/`contentRoot`/etc., `mode` has no Zod default — a config that omits it fails validation immediately instead of silently defaulting to `'dev'` (SEC-C1 follow-up: the old default could let a misconfigured prod deploy run with dev-trusting, header-based auth semantics). Tests that don't care about the value should use `defineCanopyTestConfig`/`createTestServices` (`src/config-test.ts`), which default `mode: 'dev'` for terseness; `defineCanopyConfig` (production config authoring) has no such fallback.

### Deployment Mode (`deployedAs`)

| Value      | Default | Behavior                                                                    |
| ---------- | ------- | --------------------------------------------------------------------------- |
| `'server'` | Yes     | Normal: auth plugin required, permissions enforced per-request              |
| `'static'` | No      | No request context, no auth; `STATIC_DEPLOY_USER` used; permissions skipped |

Checked via `isDeployedStatic(config)` in `context.ts`, `content-reader.ts`, `branch-workspace.ts` (short-circuits workspace creation), and `ai/resolve-branch.ts` (returns cwd). `isBuildMode()` is kept as a safety net for build-phase edge cases in server deployments.

### Dev Content Sync (`dev.contentSync`)

Dev-mode-only setting controlling how the dev server surfaces working-tree `content/**` edits made outside the editor that diverge from the served branch clone. Warn-only (it never writes). Ignored when `mode !== 'dev'`.

| Value              | Behavior                                                                    |
| ------------------ | --------------------------------------------------------------------------- |
| `'warn'` (default) | Log a warning naming the diverged files (on startup and on content changes) |
| `'off'`            | No watcher, no warnings                                                     |

There is intentionally no auto-push mode: overwriting the branch clone from the working tree would silently clobber uncommitted editor "Save" state. Reconcile explicitly via `canopycms sync push` (interactive, conflict-aware).

### Conflict Notice

Conflict indicators appear at two levels:

- **Per-entry**: `FormRenderer` accepts a `conflictNotice?: boolean` prop that displays a non-blocking informational alert when the current entry has a content conflict with the base branch. `Editor.tsx` computes this by checking whether `currentEntry.contentId` appears in `currentBranch.conflictFiles`.
- **Per-collection (navigator)**: `EntryNavCollection` has an optional `conflictNotice?: boolean` field. `EditorCollection` now carries `contentId?: ContentId` (threaded from `FlatSchemaItem` via `buildEditorCollections` in `editor-config.ts`).

`EntryNavigator.tsx` accepts a `loading?: boolean` prop: when true and the tree is empty it shows a loading indicator instead of the "No content" empty state.

### Preview URL Construction

**Location**: packages/canopycms/src/editor/editor-utils.ts

`buildPreviewSrc(entry, context)` builds the preview iframe `src`. Split in two so the deployment prefix is applied exactly once, at the end, uniformly across every branch (including the `entry.previewSrc` escape hatch):

| Function                            | Purpose                                                                                                                                                                 |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `buildRawPreviewSrc` (module-local) | The unprefixed URL: `previewSrc` override → `previewBaseByCollection` → collection path + encoded slug (index entries collapse to the collection path), plus `?branch=` |
| `buildPreviewSrc` (exported)        | `joinUrlPrefix(context.basePath, buildRawPreviewSrc(...))` — no-op when `basePath` is unset; an absolute `previewSrc` (cross-origin override) passes through untouched  |

`EditorEntry.apiPath` has been removed (it was dead); the API client owns request URLs, and its base is prefixed once by `ApiClientProvider`.

- BranchMetadata - Branch info (name, status, access, timestamps, baseBranch — fork point recorded at creation, immutable afterwards (enforced in branch-metadata.ts save()), conflictStatus, conflictFiles, pullRequestState — `PullRequestState` last observed by the worker's merge-poll or `markAsMerged`, mergedAt — ISO timestamp stamped when archived via PR merge, rebaseFailure — `{ message, firstAt, lastAt }` set by the worker when a rebase cycle fails for this branch, cleared on next success/submit, syncFailureReason — short reason the last GitHub sync task failed, set by the worker alongside `syncStatus: 'sync-failed'`, cleared on next successful sync)

### Protected Base Branch

The base branch (`config.defaultBaseBranch`, usually `main`) can never be submitted for review in either mode (submitting it would push straight to itself, bypassing review) and is read-only in the editor in prod only (dev needs it editable since the developer always lands there). See `authorization/protected-branch.ts` (`getBranchProtection`) for the single source of truth other modules key off of.

| Layer               | Enforcement                                                                                                                                                                                                                                                     |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API guards          | `writableBranch`/`submittableBranch` (api/guards.ts) — 403 before the handler runs; see API Layer above                                                                                                                                                         |
| Workflow permission | `authorization/branch.ts`'s `canPerformWorkflowAction(..., { isProtectedBranch })` disables the auto-provisioned system-branch (`createdBy: 'canopycms-system'`) grant on the base branch                                                                       |
| Branch delete       | `api/branch.ts`'s `deleteBranchHandler` rejects (400) deleting the protected base branch — it's the prod serving clone                                                                                                                                          |
| Branch listing      | `BranchListItem` (api/branch.ts) carries `isProtected`/`readOnly`, computed server-side per request                                                                                                                                                             |
| Editor UI           | `BranchManager.tsx` hides Submit and shows a "protected" badge/tooltip; `EditorHeader.tsx` disables Save/Submit and shows a `protected-branch-banner` Alert when `branchReadOnly`; both driven by `currentBranch.isProtected`/`.readOnly` from the branches API |

**Operating Modes** (`OperatingMode = 'prod' | 'dev'`):

- `prod`: Branch clones on persistent filesystem (e.g., EFS at `/mnt/efs/workspace`). Full PR workflow, real GitHub integration, task-queue-based git ops. Env var: `CANOPYCMS_WORKSPACE_ROOT`.
- `dev`: Branch clones in `.canopy-dev/` (gitignored). Full-featured branching and git ops (same as prod), but no real GitHub PRs (`supportsPullRequests()` → false). Auto-detects current git HEAD branch as `defaultActiveBranch` and `defaultBaseBranch` (fork point) when not explicitly configured.

**Strategy classes**:

| Class                  | Layer       | Mode | Key behaviour                                               |
| ---------------------- | ----------- | ---- | ----------------------------------------------------------- |
| ProdClientSafeStrategy | client-safe | prod | All features true; commits + pushes enabled                 |
| ProdStrategy           | server      | prod | Workspace root from env/EFS; auto-detects remote.git        |
| DevClientSafeStrategy  | client-safe | dev  | All features true except `supportsPullRequests→false`       |
| DevStrategy            | server      | dev  | Workspace root: `{cwd}/.canopy-dev`; auto-init local remote |

**Usage**:

```typescript
// Client components (safe for 'use client')
import { clientOperatingStrategy } from '@/operating-mode'
const strategy = clientOperatingStrategy(mode)
if (strategy.supportsBranching()) { ... }

// Server code
import { operatingStrategy } from '@/operating-mode'
const strategy = operatingStrategy(mode)
const branchRoot = strategy.getContentBranchRoot('my-branch')
```

**Settings Branch Namespacing (`deploymentName`)**

Two CanopyCMS deployments (e.g. staging + prod, or two separate apps) can share one GitHub repo without fighting over the same settings orphan branch (`canopycms-settings-{deploymentName}`, which holds `permissions.json`/`groups.json`). `getSettingsBranchName()` on both `ProdStrategy`/`DevStrategy` resolves the name via `resolveDeploymentName(config, modeDefault)` (operating-mode/deployment-name.ts), the single resolution point, in this precedence order:

| Precedence | Source                                                | Why                                                                                                                                                                          |
| ---------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 (wins)   | `process.env.CANOPYCMS_DEPLOYMENT_NAME`               | Trimmed, empty ignored; stamped per-stack by infra (canopycms-cdk's `CanopyCmsServiceProps.deploymentName`), so it's GUARANTEED TO DIFFER between deployments sharing a repo |
| 2          | `config.deploymentName`                               | Baked into the shared repo's `canopycms.config.ts`, so it's GUARANTEED TO BE IDENTICAL across deployments sharing it                                                         |
| 3          | `modeDefault` (caller-supplied, `'prod'` / `'local'`) | Mode-specific fallback when neither of the above is set                                                                                                                      |

Warns once (module-level flag) if env and config are both set and disagree, naming which one won. See `settings-workspace.ts`'s `ensureGitWorkspace` rename guard for the failure this protects against: without it, an existing settings workspace resolving to a newly-different branch name would be silently wiped (`git checkout --orphan` + `rm -rf .`) instead of refusing to boot.

### Branch Lifecycle

1. Create branch -> BranchWorkspaceManager provisions clone
2. Edit content -> Writes to branch workspace
3. Submit for merge -> Commits, pushes, creates PR via Octokit (or queues task for worker)
4. Review -> Request changes unlocks, approval locks
5. Merge -> Clean up remote branch, archive clone (via manual `markAsMerged` API, or automatically by CmsWorker's `pollMergeState` detecting the PR merged on GitHub — both share `buildMergedBranchUpdate`, see branch-metadata.ts)

### Git Operations (Service Methods)

**Location**: packages/canopycms/src/services.ts

Service methods handle git operations with automatic author handling:

| Method                     | Purpose                     | Usage                                                  |
| -------------------------- | --------------------------- | ------------------------------------------------------ |
| `commitFiles()`            | Commit specific files       | Admin changes (permissions, groups)                    |

```typescript
  context,
  files: '.canopycms/permissions.json',
  message: 'Update permissions',
})
```

**submitBranch Example** (branch-status.ts):

```typescript
await ctx.services.submitBranch({ context })
```

**Git Author Handling**: Both methods automatically call `git.ensureAuthor()` using `gitBotAuthorName` and `gitBotAuthorEmail` from config. No manual author setup needed.

**GitManager.add()**: Accepts `string | string[]` for convenience.

**Branch identity** (`services.ts` → `createActiveBranchDetector()`): Service creation resolves and bakes BOTH branch-identity fields into config so all downstream code reads one consistent value. `defaultActiveBranch` (which workspace to serve content from): explicit config wins in both modes; `dev` auto-detects from git HEAD (`git rev-parse --abbrev-ref HEAD`, 5s TTL cache); `prod` falls back to `defaultBaseBranch ?? 'main'`. `defaultBaseBranch` (fork point for new editing branches): explicit config wins; `dev` follows the same HEAD detection when unset; otherwise `'main'` (matching `resolveBaseBranch` in utils/git.ts, the canonical definition used by workspace provisioning). `content-reader.ts` uses `defaultActiveBranch` as its default branch. `services.refreshActiveBranch()` re-detects git HEAD in dev mode and refreshes both fields (each only when not explicitly configured); it short-circuits when mode !== 'dev', when both fields are explicitly configured, or when `deployedAs: 'static'`. Called by `getContext()` and the HTTP handler before each request. `createTestCanopyServices` pins both fields (`defaultBaseBranch ?? 'main'`, `defaultActiveBranch ?? defaultBaseBranch ?? 'main'`) to avoid HEAD detection in tests. Git-operating service methods (`commitFiles`, `submitBranch`) prefer the branch's recorded `context.branch.baseBranch` over the config value.

**Branded Types** provide type safety for different path semantics:

- `LogicalPath`: Content-relative paths without embedded IDs (e.g., "content/posts/my-post"); used for all collection paths
- `PhysicalPath`: Filesystem paths that may contain embedded content IDs
- `BranchName`: Git branch names (validated against git naming rules)
- `SanitizedBranchName`: Branch name safe for filesystem use
- `ContentId`: 12-character Base58-encoded content ID
- `Slug`: Single path segment for collections or entries (e.g., "posts", "my-first-post"); normalized to lowercase
- `ROOT_COLLECTION_ID`: Sentinel `ContentId` value (`'__rootcoll__'`) for the root content directory, which has no embedded ID in its name. Uses underscores to avoid collision with real Base58 IDs.

Note: `CollectionPath` brand was eliminated; use `LogicalPath` with a `content/` prefix for all collection paths.

### Branded Type Conventions

**Boundary validation** (`parse*` functions) - validate before branding, use at API/input boundaries:


| url-prefix.ts           | THE single render-time URL-prefix join. `joinUrlPrefix(prefix, path)` — returns `path` untouched when it is already a declared off-site URL (absolute-check runs FIRST, or an off-site canonical becomes `<prefix>/https://…`), treats an empty/all-slash prefix as no prefix (also kills a `'//'` prefix, which a browser reads as protocol-relative), passes a declared off-site prefix through as-is, and adds a leading slash to a bare same-origin prefix (without it, `preview-123` yields a _document-relative_ URL that resolves differently per page); non-absolute paths go through `neutralizeImplicitOffOrigin` (sanitize-href.ts) so a backslash-equivalent spelling can't be read as protocol-relative. `isAbsoluteUrl(url)` — declared off-site pointer (scheme-qualified or literal `//host`); deliberately narrower than "resolves off-origin". `stripTrailingSlashes(value)` — linear character scan, not `replace(/\/+$/, '')` (polynomial-ReDoS shape, CodeQL `js/polynomial-redos`; both callers' prefixes are adopter/env-supplied). | occ-json-write.ts       | Shared OCC (optimistic-concurrency-control) JSON write helper, extracted from near-identical logic previously duplicated in comment-store.ts and branch-metadata.ts (both now adopt it, alongside authorization/settings-file-store.ts's `mutateSettingsJsonFile` for permissions.json/groups.json): `OccWriteConflictError`; `writeOccJsonFile(filePath, payload, { expectedVersion, settleMs?, trailingNewline? })` — temp-file write, version precheck, atomic rename (or temp+`link()` exclusive-create for new files), settle wait, writeId read-back verification; `withOccRetry(operation, { maxAttempts?, isRetryable? })` — retries on `OccWriteConflictError` with exponential backoff + jitter, caller reloads state each attempt; `withOccFileLock(filePath, fn)` — server-enforced mutual exclusion via `proper-lockfile` (mkdir-based, immune to client-side NFS caching), for writers where a cross-host lost update is unacceptable. See docs/concurrency.md for the guarantee/non-guarantee boundary between OCC alone and the lockfile layer.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| provisioning-lock.ts    | Cross-process filesystem lock (via `proper-lockfile`) for content provisioning, so parallel build-worker processes (or admin requests) don't race creating/mutating the same git workspace. `acquireProvisioningLock(lockTargetDir, lockName)` — patient variant, ~600 jittered retries (minutes) for build workers that can afford to wait on a live provisioner. `tryAcquireProvisioningLock(lockTargetDir, lockName)` — zero-retry sibling for a synchronous request/response cycle (e.g. Lambda-backed admin handlers); throws immediately with `err.code === 'ELOCKED'` on live contention instead of retrying, so callers can translate that into a 409. Both share `stale: 30_000` staleness recovery; used by branch-workspace.ts's `ensureGitWorkspace()` and by `api/admin-branch-health.ts`'s purge handler (which also reads the same lock's mtime via branch-health.ts's `provisioningLockPath` to gate on freshness)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

**Error Handling Pattern**:

```typescript
import { getErrorMessage, isNotFoundError } from '../utils/error'

try {
  await fs.readFile(path)
} catch (err: unknown) {
  if (isNotFoundError(err)) return null
  throw new Error(`Failed: ${getErrorMessage(err)}`)
}
```

**Atomic Write Pattern** (used by content-store.ts, schema-store.ts): permissions.json/groups.json (authorization/permissions/loader.ts, authorization/groups/loader.ts) no longer call `atomicWriteFile` directly — they write through `mutateSettingsJsonFile` (authorization/settings-file-store.ts), whose OCC layer (`writeOccJsonFile`, occ-json-write.ts) does its own temp-file+rename write under the cross-host lock.

```typescript
import { atomicWriteFile } from '../utils/atomic-write'

await atomicWriteFile(filePath, JSON.stringify(data, null, 2) + '\n')
```

**Location**: packages/canopycms/src/ai/

| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**Transform hooks on `AIContentConfig`** (all keyed by entry type):

- `fieldTransforms` / `componentTransforms` / `bodyTransforms` — field-, JSX-component-, and body-level rewrites (body transforms fire for MD/MDX only).
- `entryTransforms?: EntryTransforms` (`Record<string, EntryTransformFn>`) — entry-level hook that runs once per entry at generation time and appends returned markdown after the body/fields. Fires for every format (including data-only JSON/YAML), unlike `bodyTransforms`. Output flows automatically into the per-entry file, the collection `all.md`, and bundles.
- `EntryTransformFn = (entry: AIEntry, ctx: EntryTransformContext) => Promise<string | undefined> | string | undefined`; `EntryTransformContext = { contentId; readSibling(name) }`. `ctx.readSibling` is traversal-guarded (rejects slashes/`..`/absolute paths, resolves null if the file is missing), letting an adopter fold a colocated sibling artifact (e.g. `<contentId>.profile.json`) into AI output without exposing the entry's absolute path. A throwing transform is logged and skipped; the entry still renders without the appended section.

**Caching strategy in `createAIContentHandler()`**:

- `prod`: result cached for the process lifetime (Lambda instances recycled on deploy, so fresh on each deploy)
- `dev` (`mode !== 'prod'`): cache cleared on every request so content changes are reflected immediately without restarts

**Schema cache**: Uses `BranchSchemaCache` (file-based); no special in-memory path.

**Cache-Control headers**: `no-cache` when `mode !== 'prod'`; `public, max-age=60` in prod.

**Static file generation** (`src/build/generate-ai-content.ts`, `generateAIContentFiles()`): writes AI content to disk (e.g. `public/ai`) for the `canopycms generate-ai-content` CLI command. Unconditionally validates every entry via `assertBuildEntriesValid` (`static/index.ts`) before generating — no `isBuildMode()` gate, since this is an explicit build command rather than something `next dev` runs incidentally. Returns `{ fileCount, removedCount, outputDir }` and PRUNES output a previous run wrote that this run no longer produces (e.g. a renamed/re-modelled entry's stale file). What a run wrote is tracked in `GENERATED_RECORD_FILENAME` (`.canopy-generated.json`) — deliberately NOT the published `manifest.json`/`AIManifest` shape adopters consume. The record is written as the union of old+new files before any file is written (so a part-way failure still leaves a superset the next run can clean), and only files a _previous run of this tool_ recorded are ever deleted — never a directory sweep, since the output directory belongs to the adopter.
